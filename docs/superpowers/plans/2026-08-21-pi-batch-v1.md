# Pi Batch V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a thin DevSpace MCP facade that launches 1-8 independent Pi investigations concurrently under a hard read-only tool boundary and returns their lifecycle/results to the host.

**Architecture:** Reuse the existing `PiRpcLocalAgentAdapter` for every worker. Add one small in-memory `PiBatchManager` that owns batch grouping and worker states, and register three MCP tools in `server.ts`; the host remains the only reducer. Keep modification discipline in the seeded `devorder` skill rather than growing the batch API.

**Tech Stack:** TypeScript, Node.js, Zod, MCP SDK, existing Pi RPC adapter.

**Spec:** `docs/superpowers/specs/2026-08-21-pi-batch-v1-design.md`

## Global Constraints

- V1 exposes only `pi_batch_start`, `pi_batch_status`, and `pi_batch_results`.
- Every Pi batch worker is hard-coded `read_only`; there is no permission parameter.
- A batch contains 1-8 independent workers; 9+ is rejected rather than queued.
- Pi may read broadly across the workspace, but cannot mutate repository state.
- DevSpace does not synthesize, vote over, steer, or allow communication between worker answers.
- No A2A, snapshot-consistency protocol, DAG scheduler, write-capable Pi batch, persistence across server restart, or Claude fallback.
- Apply `devorder`: findings in green working code are technical debt unless the requested outcome, current failure, or a concrete near-term failure authorizes mutation.

- [ ] **Step 3: Implement only the batch grouping/lifecycle**

Use an internal `Map<string, PiBatchRecord>` and start each worker immediately without awaiting siblings:

```ts
export const MAX_PI_BATCH_WORKERS = 8;

type PiRunner = (input: LocalAgentRunInput) => Promise<LocalAgentRunResult>;

export class PiBatchManager {
  private readonly batches = new Map<string, PiBatchRecord>();

  constructor(
    private readonly runPi: PiRunner = (input) => runLocalAgentProvider("pi", input),
  ) {}

  start(workspace: string, tasks: PiBatchTask[]): PiBatchStartResult {
    validateTasks(tasks);
    const batch = createBatchRecord(tasks);
    this.batches.set(batch.id, batch);
    for (const task of tasks) {
      void this.runWorker(batch, task, workspace);
    }
    return this.status(batch.id);
  }

  private async runWorker(batch: PiBatchRecord, task: PiBatchTask, workspace: string): Promise<void> {
    const worker = batch.workers.get(task.id)!;
    try {
      const result = await this.runPi({
        prompt: task.prompt,
        workspace,
        writeMode: "read_only",
      });
      worker.status = "completed";
      worker.result = result.finalResponse;
    } catch (error) {
      worker.status = "error";
      worker.error = error instanceof Error ? error.message : String(error);
    }
  }
}
```

Return copied public objects from `status()`/`results()` rather than exposing mutable records. Batch status is `completed` when no worker remains `running`, even if one or more workers ended in `error`.

Do not add queues, retries, persistence, cancellation, steering, result schemas, or session resumption.
